GenAI in compliance: where it helps today, and what v2 can do

A general-level view of how generative AI fits a compliance platform — extraction, matching, reasoning and communication — with concrete v2 levers across dashboards, risk prioritisation, control identification and beyond, anchored to what the code already does.

Where GenAI sits in the product today

One capability, done well — and a deliberately deterministic core around it.

The single AI capability

When an instrument is scraped or uploaded, OCR text is sent to an LLM which returns a structured ClassificationResult: area of focus, nature, risk rating + explanation, applicability + confidence, act, dates, licence types, an AI summary, and — critically — a list of obligations (verbatim description + interpreted statement, section, type, recurring deadline, area, risk description, likelihood, impact, control owner) and sanctions (penalty, liable roles, type). It is chunked (~15k chars) and merged, provider-agnostic (primary + fallback with cooldown), and uses Spring AI native structured output.

Everything else is deterministic — on purpose

Compliance state, requirement coverage, gap ("no control"), control effectiveness, residual risk, banding, deadline rules, de-duplication, escalation ladders, the task queue and the score are all computed by rules from accepted evidence. No LLM asserts compliance.

Why that is the right base for v2

Because the truth layer is deterministic and auditable, GenAI can be added as an advisory layer — suggestions, retrieval, narratives — without ever becoming the source of record. That is what makes AI usable in a regulated setting.

How GenAI helps compliance at a general level

Four verbs. Every credible AI-in-compliance feature is one of these applied to the chain below.

1 · Extract
Unstructured → structured text: instruments, obligations, sanctions, deadlines, clauses, evidence metadata. Done today.
2 · Match / map
Semantic linking: obligation↔control, obligation↔framework clause, obligation↔obligation (dup), evidence↔requirement, old↔new instrument. v2 sweet spot.
3 · Reason / prioritise
Judgement with justification: risk scoring, gap analysis, "why does this apply?", evidence sufficiency, anomalies.
4 · Communicate / act
Language out: board narrative, escalations, filing drafts, natural-language query, the assistant, test scripts.

Dashboards & insight

The dashboard is already derived and URL-backed — which makes it the easiest place to add GenAI safely.

Natural-language query on the registers

A query box that turns English into the typed filters that already exist — "High-risk AML obligations with no control", "returns due in 30 days not started", "controls owned by IT Security never tested".

Screen: Obligations register / Compliance Universe / Tasks. How: the LLM maps the question to {area, risk, noControl, regulator, dueWindow…} via tool-calling — it never writes SQL, it fills the same URL filters the UI already applies. Low risk, immediately useful.

Executive & board narrative

Generate a readable summary from the live snapshot and the day-over-day delta — "score 45% (▼2); driven by 3 overdue CBN filings and 12 uncovered AML requirements; 2 controls regained effectiveness after remediation."

Screen: Dashboard, Rendition & Coverage, Reports. Deterministic numbers; the LLM writes the sentences.

Anomaly explanations

When a KPI moves outside a band, explain it: "returns on-time fell 12% — the CBN FX weekly slipped to late filing." Root-cause prose over the existing trend data.

Principle

Every number stays computed; AI only finds (NL query) and describes (narrative). No metric is ever AI-generated.

Risk prioritisation

Inherent is a judgement; residual is already deterministic. AI improves the judgement and explains the movement.

Suggested inherent risk with a rationale

Classification already extracts likelihood, impact and risk_description. v2 turns those into a proposed 5×5 band plus a cited justification the analyst accepts or edits. Banding stays rule-based; the AI only proposes the inputs.

Screen: obligation risk block. Example: "Proposed High (L4×I5) — direct systemic exposure if capital adequacy lapses; sanction ₦500m."

Residual narrative (deterministic trigger, AI prose)

The residual is already derived live from accepted control tests. AI writes the "why": "Residual lowered to Moderate — the identity-verification control passed on 2026-10-18 (2 of 3 controls effective)."

Risk theming & clustering

Group 300+ obligations into a handful of board-level themes ("AML/CFT programme hygiene", "data-protection governance") by semantic similarity — so the board sees 6 risks, not 340 rows.

Prioritisation scoring

A configurable materiality × exposure score with an explanation, to rank what the analyst touches first — tunable per firm, never a black box (weights are explicit).

Control identification & mapping headline v2

The biggest manual burden is answering "what do we already do about this duty, and what should we do?". This is a matching problem — exactly what embeddings + an LLM re-ranker solve.

1 — Recommend existing controls

Given an obligation or a single requirement, retrieve the tenant's existing controls semantically and suggest a shortlist with a reason: "CTL-0142 Identity Verification Check covers this — it tests the same KYC duty." One click to link, one to dismiss.

Screen: Obligation detail → Requirements (the coverage row), Link-controls picker.

2 — Draft a missing control

When nothing fits, generate a draft control in the toolkit's own vocabulary — name, what it does, how tested, test frequency, suggested owner, evidence type — for the analyst to edit and accept. Turns a blank form into a starting point.

3 — Framework crosswalk

Map each obligation to the clauses it satisfies (ISO 27001:2022, NIST CSF, NDPA, CBN RBCSF…), auto-populating the same framework-mapping that runbooks use. Answers "are we ISO-ready?" without a spreadsheet.

4 — Tame control sprawl (semantic dedup)

The seeded tenant carries ~2,137 controls with many near-duplicates. Embeddings surface "these 5 controls are the same control" for merge — complementing the existing natural-key dedup.

5 — Map runbooks ↔ controls

Suggest which controls a runbook procedure evidences, speeding the coverage matrix.

Method & safety

Embeddings (pgvector) for recall → LLM re-ranker for precision with a reason → human accepts. Every suggestion stores model, prompt hash, confidence and the accept/reject, so the AI's advice is itself auditable.

Other v2 levers

Regulatory change monitoring

When a new instrument arrives, semantically diff against the existing act/section it amends: "Section 4 changed — adds a 24-hour ATM funding duty; existing obligation O-1188 needs updating." This is the sharp end of Pain Point 1.

Evidence intelligence

Read uploaded evidence and judge sufficiency: is this actually a test result? a policy extract? Extract date/outcome, flag a mismatch with the claimed result, and auto-suggest the subject it belongs to.

Deadline extraction fallback

The rule parser handles most wording; for the messy remainder (the ~50 "Due date needed" returns) the LLM proposes a due-date rule and shows the source phrase for confirmation.

Test-script generation

Draft the "how tested" steps, sample size and evidence to collect for a control, from its linked obligation text.

Communicate: escalations, filings, review summaries

Personalise escalation emails; summarise a 60-page filing for the reviewing CCO; pre-draft a remediation note.

The assistant (RAG over the tenant's own universe)

A grounded chat: "what proves our KYC duty?", "what's our NDPA exposure?", "which controls were never tested?" — with citations to obligations, controls, tests and evidence, respecting RBAC and tenant scope. Read-only; it points, it does not act.

Onboarding assist

Suggest a sensible starter control set for the tenant's licence types and regulators, so a new institution is not staring at an empty controls register.

Guardrails & risks

Hallucination

Mitigate with retrieval over the tenant's own data, mandatory citations, confidence thresholds, and human accept/edit. Never let AI author a compliance state.

Defensibility

Every AI suggestion is logged (model, prompt hash, output, decision, actor) on the hash-chained trail, so "why did we do this?" is answerable years later.

Prompt injection

Regulatory documents and uploaded evidence are untrusted input. Treat all retrieved content as data, never as instructions; sandbox tool-calling to read-only, typed calls.

Data isolation & residency

Send only the calling tenant's data; never cross tenants in a prompt or a vector index; respect PII and any residency constraints on the model provider.

Cost & latency at scale

1,400+ obligations × many tenants — embed once, cache, route cheap tasks to small models, batch; keep the interactive path (query, assistant) fast and cheap.

Over-reliance & drift

Golden-set evals in CI, confidence gating, and keeping the deterministic core authoritative so a bad model release cannot change a compliance verdict.

Deep dive — the expanded explanations

The summary tabs say what each v2 capability is. This tab says how it works end to end: the data it reads and writes, a concrete example, and where it plugs into the product. Read the substrate first — most features are built on it.

A · The matching substrate foundation

What it is

Almost every v2 feature — control recommendation, framework crosswalk, dedup, the assistant — is the same primitive: embed a piece of text, find the nearest neighbours, then let an LLM re-rank them and give a reason. Build it once as a shared service and the features become thin.

How it works

  • Embed at write time. Whenever an obligation, requirement, control or framework clause is created or edited, compose a canonical string (title + text + area) and call an embedding model once; store the vector and a content hash. Re-embed only when the hash changes.
  • Store in pgvector. Postgres already runs the app — add the vector extension and one column per embeddable table (or a single polymorphic embeddings table).
  • Retrieve. At query time, embed the query text and run an approximate-nearest-neighbour search scoped to the tenant, filtered by type/status, top-K (say 20).
  • Re-rank & explain. Feed the query + the K candidates to an LLM and ask for a shortlist with a one-line reason and a confidence each. This is where precision comes from — vectors give recall, the LLM gives judgement.
  • Record the suggestion. Write the outcome to the ledger (see L) so it is auditable and can train future thresholds.
-- illustrative pgvector shape (one column per embeddable table) ALTER TABLE requirements ADD COLUMN embedding vector(1536); ALTER TABLE requirements ADD COLUMN embed_hash text; CREATE INDEX ON requirements USING hnsw (embedding vector_cosine_ops); -- polymorphic alternative: one table for everything searchable CREATE TABLE embeddings ( id bigserial PRIMARY KEY, tenant_id bigint NOT NULL, subject_type text NOT NULL, -- obligation | requirement | control | clause | evidence subject_id bigint NOT NULL, content_hash text NOT NULL, embedding vector(1536) NOT NULL, updated_at timestamptz NOT NULL DEFAULT now() ); CREATE INDEX ON embeddings USING hnsw (embedding vector_cosine_ops); CREATE UNIQUE INDEX ON embeddings (subject_type, subject_id);

Where it plugs in

A single Spring service (SemanticMatcher) with two methods — nearest(type, text, k) and rank(query, candidates) — that every feature calls. Embedding calls reuse the existing provider-agnostic AiClient pattern (primary + fallback + cooldown), so a provider outage degrades gracefully rather than breaking a screen.

B · Control recommendation — how it actually works

Steps

  • Trigger: the analyst opens a requirement (or clicks "Suggest controls") on the Obligation detail → Requirements tab.
  • Query text: the requirement's text + its obligation title + area of focus.
  • Retrieve: nearest controls in the same tenant, active, and excluding ones already linked to this obligation; K = 20.
  • Re-rank: the LLM returns the best 1–3 with a reason and confidence, and is instructed to return none if nothing genuinely covers the duty (abstention is a feature, not a failure).
  • Present & link: a compact list — "CTL-0142 Identity Verification Check — covers this KYC duty (high)" — with Link per row. Linking calls the existing PUT /requirements/{id}/controls; nothing new is invented.
GET /api/v1/requirements/{id}/control-suggestions?limit=3 200 OK { "requirementId": 4471, "suggestions": [ { "controlId": 142, "controlNumber": "CTL-0142", "name": "Identity Verification Check", "confidence": "high", "reason": "Tests the same KYC customer-identity duty this requirement states." }, { "controlId": 219, "controlNumber": "CTL-0219", "name": "CDD Onboarding Review", "confidence": "medium", "reason": "Partially overlaps - covers onboarding checks, not ongoing verification." } ] }

Three worked examples

  • Direct match. Requirement: "Verify customer identity before account opening." → CTL-0142 (high). One click links it; the requirement's state moves from No control to Partial/Compliant once a test is accepted.
  • Partial match. Requirement: "Screen all new customers against sanctions lists." → CTL-0219 covers onboarding but not ongoing screening (medium). The reason tells the analyst it is partial, so they can link it and raise a gap for the ongoing part.
  • Promote to draft. Requirement: "Report data-protection breaches to NDPC within 72 hours." → no control found. The analyst clicks Draft a control and gets a pre-filled candidate (Detective, evidence = notification log, monthly test) to edit and save.

Precision tactics

Exclude already-linked controls; cap suggestions per obligation (avoid 30-row dumps); always show the reason so a wrong suggestion is obviously wrong; and log dismissals — a dismissed pair is negative training signal and can raise the similarity floor over time.

C · Framework crosswalk

How it works

The runbook framework library already holds 34 frameworks / 243 clauses (ISO 27001:2022, NIST CSF, NDPA, CBN RBCSF…). Embed each clause, then for every obligation retrieve the nearest clauses and let the LLM confirm and cite: "NDPA s.40 — you must notify the Commission of a breach; your obligation O-1188 implements it." The result is a proposed clause mapping the analyst can accept.

Value

Answers "are we ISO-ready?" or "how does this map to NDPA?" as a filtered view instead of a spreadsheet — and it feeds the runbook coverage matrix, which already speaks in clause terms. The mapping is a suggestion, so a false positive is a one-click reject.

D · Semantic de-duplication (taming sprawl)

How it works

Vector search is also the best duplicate detector. For each obligation/control, find near-identical neighbours (cosine ≥ a high threshold), then confirm with the LLM ("are these the same duty/control?"). Present them as merge candidates with the shared intent; the analyst merges or ignores.

Example

The seeded tenant has ~2,137 controls with many near-duplicates ("Annual policy review" appearing several times per act). Today, de-duplication is by natural key only; embeddings surface the semantic duplicates the key misses — "these five controls are effectively one" — so the register reflects reality and coverage stops being inflated by clones.

E · Natural-language query → filters

How it works

A single tool-calling step: the LLM receives an allow-list of the filter parameters that already exist and must return a structured filter object, never SQL. The UI applies that object to the same URL-backed filters it uses today, so the result is exactly what a human clicking the filters would see.

Only allowed parameters; always render the interpreted query back as filter chips ("AML/CFT/CPF · High · No control") so a misread is visible before results; no SQL, no free-form database access.

F · Risk prioritisation — expanded

1 — Proposed inherent risk

Classification already extracts likelihood, impact, risk_description and the sanction. v2 turns that into a proposed 5×5 band plus a cited rationale; the analyst accepts or edits. The band itself is still computed by the rule engine — the AI only proposes the inputs.

Example (real pattern): "Proposed High (L4 × I5). Rationale: failure to maintain capital adequacy threatens systemic stability; maximum sanction ₦500m."

2 — Residual narrative

Residual is already derived live from accepted control tests. The AI writes the sentence the analyst would otherwise have to assemble: "Residual lowered to Moderate — the identity-verification control passed on 2026-10-18; 2 of 3 linked controls effective." Deterministic trigger, AI prose.

3 — Risk theming

Cluster obligations/risks by embedding similarity into a handful of board-level themes ("AML/CFT programme hygiene", "data-protection governance"), so leadership sees six risks instead of 340 rows. Each theme lists its member obligations for drill-down.

4 — Prioritisation score

A configurable materiality × exposure score with an explicit breakdown — never a black box. The AI can propose the materiality inputs, but the weights are firm-set and the arithmetic is deterministic.

G · Dashboard narratives & anomaly explanations

How it works

The daily snapshot plus the day-over-day delta is fed to the LLM with a strict template: numbers are passed in (never computed by the model), and the model only writes prose. Anomaly detection is a rule (a KPI outside its band); the LLM then explains the most likely driver from the per-regulator / per-bucket deltas.

Example

"Compliance score 45% (▼2 vs yesterday). Drivers: 3 overdue CBN filings, 12 uncovered AML requirements; offset by 2 controls regaining effectiveness after remediation." Every figure is clickable to its rows; the model added only the connective tissue.

H · Regulatory change monitoring

How it works

  • When a new instrument is ingested, match it to the existing act/section it amends (by reference number, else embedding).
  • Diff the classified obligations: added, removed, changed (by semantic similarity of the duty text).
  • Raise a change alert per material difference with a before/after and a suggested action ("update obligation O-1188", "new duty — no control").

Example

"CBN Circular X amends Circular Y, Section 4: adds a 24-hour ATM funding duty (previously 48h). Existing obligation O-1188 needs updating; no control currently covers the tightened window." This is the sharp end of Pain Point 1 — not just "a new document arrived" but "here is what changed and what to do."

I · Evidence intelligence

How it works

On upload, extract the text and let the LLM: classify the document type (test result, policy extract, remediation proof, filing receipt), pull the date and outcome, check it against the claimed result, and suggest the subject it belongs to. Flag mismatches ("this is a policy extract, not a test result") rather than silently storing it.

Example

A tester uploads a PDF claimed as a PASS. The extractor reads it, finds no test date or result table, and returns "looks like a policy extract" — so the reviewer opens it with a warning instead of trusting the label. Where it is a result, the date/outcome pre-fills the record.

J · Deadline extraction fallback

How it works

The deterministic parser handles most regulator wording (rule: DATE, OFFSET, or event-driven). For the messy remainder it currently leaves ~50 returns at "Due date needed". v2 adds an LLM fallback: propose a rule and quote the source phrase, so the analyst confirms with the evidence in front of them.

Example

Regulator text: "within 3 months after year-end". Parser gets nothing → LLM proposes OFFSET 90 days after period end (→ 31 Mar), quoting the phrase. The analyst accepts; the schedule regenerates untouched periods. The rule, once set, is deterministic — the AI only proposed it.

K · The assistant (RAG over the tenant's own universe)

Flow

  • Scope to the caller's tenant and role (RBAC applies — an analyst and a CCO may see different things).
  • Retrieve the top obligations/controls/tests/evidence for the question via the substrate.
  • Compose an answer that cites the rows it used, and refuses when the retrieved context does not support an answer.
  • Read-only — the assistant points; it never writes. Every answer links to the exact rows so the human verifies in one click.

Example

Q: "What proves our KYC obligation?" A: "Requirement R-4471 (Verify customer identity before account opening) is covered by CTL-0142 Identity Verification Check; its latest accepted test passed on 2026-10-18 with evidence attached." — with links to the requirement, control and test. "Which controls were never tested?" returns the list, each linking to the control.

L · Architecture reference

Embedding pipeline

Compose canonical text → call embed model → store vector + content hash → re-embed on hash change. Batch nightly for backlog; embed inline for new rows. Cache query embeddings for the session.

CREATE TABLE ai_suggestions ( -- auditable advisory layer id bigserial PRIMARY KEY, tenant_id bigint NOT NULL, feature text NOT NULL, -- control_recommendation | crosswalk | dedup | nl_query | change_diff | narrative subject_type text NOT NULL, subject_id bigint, model text NOT NULL, prompt_hash text NOT NULL, output jsonb NOT NULL, confidence text, decision text, -- accepted | rejected | ignored (null until actioned) decided_by bigint, decided_at timestamptz, created_at timestamptz NOT NULL DEFAULT now() );

Eval harness

Golden sets per feature (e.g. 100 requirement→control pairs with known answers). Metrics: precision@k, recall, and abstention rate. Gate prompt/model changes in CI — a model swap that degrades mapping cannot ship silently.

Provider routing & cost

Route by task: embeddings and dedup to a small/cheap model; mapping and reasoning to a frontier model. Embed once and cache; keep the interactive path (NL query, assistant) on the fast model. The existing primary/fallback client already abstracts the provider, so routing is configuration, not rework.

M · Guardrails — expanded

Prompt injection is the top risk

Regulatory PDFs and uploaded evidence are untrusted input and must be treated as data, never as instructions. Delimit retrieved content, instruct the model to ignore imperative text inside documents, and never let a document trigger a tool call. Tool-calling is restricted to read-only, typed, allow-listed functions.

No autonomous state

The AI never writes a compliance state, links a control, or closes a finding by itself. It proposes; a human accepts; the deterministic core computes the result.

Defensibility

Each suggestion is on the ledger (model, prompt hash, output, decision, actor), so an examiner can ask "why did you link this control?" and get an answer years later, on the same hash-chained trail as everything else.

Confidence & abstention

A confidence field on every suggestion, and a similarity/temperature floor below which the system returns nothing rather than a plausible-looking wrong answer.

Isolation, residency, cost, drift

Only the calling tenant's data enters a prompt or vector index; respect PII and provider residency; embed once and cache to control cost; and keep CI evals plus the authoritative deterministic core so a bad model release cannot change a verdict.
